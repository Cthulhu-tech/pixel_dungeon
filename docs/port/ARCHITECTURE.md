# Архитектура браузерного порта

Статус: целевая архитектура; её наличие в документации не означает, что код реализован.

## 1. DDD без лишней инфраструктуры

Приложение — модульный монолит. Предметные контексты:

- **run/gameplay**: текущее прохождение и все игровые правила. Очередь ходов, сетка, бой, предметы и эффекты — его внутренние модули, а не искусственно независимые микросервисы.
- **profile**: постоянный прогресс, записи завершённых забегов, достижения и настройки. Получает явно сформированные результаты/события run, не управляет боем.
- **presentation/application shell**: ввод, окна, сцены, визуальное воспроизведение, звук и жизненный цикл приложения. Не определяет правила игры.

Граница самостоятельного модуля определяется его правилом и владельцем данных. Один портируемый класс не обязан становиться отдельным модулем. Модули ниже могут уточняться после полного аудита при сохранении зависимостей, тестируемости и единственного владельца состояния; нельзя дробить систему ради количества папок.

## 2. Целевая структура

```text
src/                         # исходная Java-игра, не изменять
assets/                      # исходные ассеты, не изменять
res/                         # исходные Android-ресурсы, не изменять
web/
  src/
    app/
      bootstrap.ts           # composition root: создаёт и соединяет реализации
      run-coordinator.ts     # порядок межмодульных действий, не копия всех правил
      flows/                 # XState-сценарии приложения/ввода
    modules/
      compatibility/         # Java-числа и совместимые алгоритмы Random
      turns/                 # логическая очередь и время акторов
      grid/                  # карта, клеточные запросы, путь, видимость, баллистика
      generation/            # комнаты, этажи, размещение контента
      actors/                # герой, существа, AI и их инварианты
      combat/                # расчёт и порядок разрешения атак
      items/                 # экземпляры предметов, инвентарь, экипировка
      effects/               # buffs, blobs и правила их жизненного цикла
      quests/                # NPC-сценарии и состояние заданий забега
      run/                   # создание/переходы/завершение забега, общие счётчики
      profile/               # прогресс между забегами, настройки, рекорды
    contracts/               # только минимальные действительно общие типы
    adapters/
      phaser/                # сцены, sprites, камера, input, audio, playback
      rex-ui/                # оригинальные окна и layout поверх rex
      zustand/               # UI-проекции, selectors, подписки
      persistence/           # browser storage, экспорт/импорт save DTO
    content/                 # извлечённые оригинальные определения и asset mapping
  tests/
    unit/
    contracts/
    parity/
    e2e/
    architecture/
  package.json
  tsconfig.json
  vite.config.ts
tools/port/                  # аудит исходников, экспорт fixtures, сравнение
tests/reference/             # независимые эталонные данные
```

Это схема, а не требование создать пустые папки. `index.ts` — единственный внешний вход модуля; внутри по необходимости `domain/`, `application/`, `ports/`, тесты. Общее имя `contracts/` не разрешает складывать туда реализацию или весь GameState.

## 3. Владение состоянием

| Состояние/правило | Владелец | Что получают другие |
| --- | --- | --- |
| Очередь, scheduled time, current actor, continuation | turns | узкие команды/снимок очереди |
| Terrain, occupancy, explored/mapped, геометрические запросы | grid | CellId, маски/readonly DTO, результаты запросов |
| HP, позиция существа как его атрибут, характеристики, состояние AI | actors | ActorId, readonly snapshot, команды сущности |
| Формулы атаки и последовательность стадий | combat | результат расчёта/команды на изменение владельцам |
| Предметы, стеки, inventory/equipment и идентификация | items | ItemId, InventorySnapshot |
| Время жизни и внутренние поля эффектов | effects | эффекты/модификаторы через контракты |
| Статус задания и диалога в забеге | quests | QuestSnapshot, допустимые действия |
| Этаж, золото и прочие общие счётчики забега | run | RunSnapshot |
| Завершённые забеги, достижения, пользовательские настройки | profile | ProfileSnapshot |
| Меню, загрузка, выбор цели, режим взаимодействия | XState flow | состояние интерфейсного сценария |
| Производные данные HUD, hover, scroll, открытая вкладка | Zustand vanilla | UI read model |
| Координаты рисования, tween, display object, audio handle | Phaser/rex | визуальное представление |

Позиция в actors и occupancy grid — не два независимо изменяемых источника правды: перемещение — одна согласованная операция application-уровня. Она проверяет возможность хода, обновляет владельца позиции и индекс занятости, затем публикует результат. Между шагами наружу не отдаётся полусостояние. Аналогично расход предмета, урон и смерть не реализуются разрозненными UI callbacks.

Таблица задаёт начальные границы, а не разрешает дублировать счётчик, если аудит обнаружит его иной естественный владелец. Любое уточнение фиксируется до изменения зависимостей.

## 4. Разрешённые зависимости

```text
bootstrap -> application flows/coordinator -> public module APIs
adapters -> contracts/ports и публичные DTO модулей
module application -> собственный domain + требуемые ports
module domain -> собственные сущности/алгоритмы + минимальные чистые типы
```

В домене запрещены framework/browser imports, import адаптера, доступ к глобальной сцене и storage. Из модуля A запрещён deep import `modules/B/domain/...`. Домен не получает огромный контекст со всем приложением: интерфейс отражает только реально необходимые операции.

Межмодульные зависимости должны быть ацикличны. При взаимной потребности coordinator связывает узкие порты, объявленные на стороне потребителя. Небольшая явная чистая зависимость через публичный API допустима, если её можно перенести вместе с модулем и она не образует цикл. Не вводить абстракцию для каждого внутреннего вызова.

DI выполняется конструктором/фабрикой в bootstrap. DI-контейнер, singleton registry и глобальный event bus не нужны. Типизированные локальные события допустимы для уже произошедших фактов; критический порядок игрового разрешения задаётся явно, а не порядком произвольных listeners.

## 5. Команда → правила → представление

```text
input/rex -> typed command -> application coordinator
          -> turn scheduler + доменные операции
          -> domain events / ordered presentation requests
          -> immutable UI projection + Phaser playback
```

Один владелец принимает решение о допустимости команды и её цене в ходах. UI может показать подсказку, но не обойти проверку. Каждый boundary валидирует внешние данные; ошибки не превращаются в молчаливый успех.

XState не хранит вторую карту/героя, не обходит Actor.time и не вычисляет combat. XState здесь также не обязан создавать отдельного actor на каждого монстра: доменный Actor оригинала и actor XState — разные понятия. AI переносится как доменное поведение; дополнительная FSM допустима только с точным соответствием исходным переходам.

Zustand использует `createStore` из `zustand/vanilla`. Сценам выдаётся интерфейс чтения/подписки, а не право произвольного setState игровых полей. Проекции имеют revision и могут быть пересозданы из одного согласованного domain snapshot. UI предпочтения имеют одного владельца; постоянные настройки сохраняет profile через storage port.

## 6. Важное исключение: анимация и очередность оригинала

В исходном Actor.process() проверяется `sprite.isMoving`; завершение действия может разблокироваться через Actor.next(). Простой перенос в «весь ход сразу, затем картинка» способен изменить поведение.

Нужен явный **continuation protocol**: action/continuation ID, тип ожидаемого завершения и проверенный порядок resume. Игровые решения остаются в домене/application; renderer лишь подтверждает завершение уже запрошенного воспроизведения. Повторное или устаревшее подтверждение игнорируется/диагностируется, но не создаёт второй ход. При уничтожении сцены оставшиеся handles закрываются явно.

Место commit урона, расхода предмета и прочих изменений определяется исходным кодом, включая callback-фазы. Не переносить всё автоматически в начало или конец анимации. Headless adapter воспроизводит тот же порядок подтверждений без Phaser. Скорость кадров меняет длительность показа, но не цены действий, RNG-последовательность и результаты команд.

## 7. Как вынести модуль

Для каждого модуля обязательны:

1. Публичный entrypoint с типами/фабриками; нет доступа к внутренним классам соседа.
2. Явно перечисленные внешние зависимости и dependency injection только нужных портов.
3. Тесты, запускающиеся в Node без Phaser/DOM/глобального singleton.
4. Собственные инварианты, сериализуемые DTO при наличии сохраняемого состояния и стабильные ID, не имена JS-конструкторов.
5. Отсутствие скрытых asset URLs, импортов store, process.env и путей к приложению.
6. `dispose()`/отписка только там, где есть реальные ресурсы; чистым алгоритмам фиктивный lifecycle не нужен.

На каждом этапе хотя бы один затронутый модуль проверять из минимального test host с fake ports. Это демонстрация переносимости, а не обещание, что скопированный каталог не имеет никаких зависимостей. Чистые общие контракты и лицензии переносятся вместе с ним.

## 8. OOP / SOLID / KISS / DRY в практике

Entity защищает инварианты (например, переход живого существа в смерть), value object описывает значение, чистая функция вычисляет алгоритм. Не создавать Anemic GameManager, который изменяет все поля всех моделей. Но не оборачивать каждое число в класс без выгоды.

Общие алгоритмы и определения имеют одно место. Различающиеся эффекты оригинала остаются различающимися, даже если несколько строк совпадают. Декларативные данные подходят для исходных таблиц; поведение остаётся явным TS-кодом. Не строить свой DSL/JSON-интерпретатор или рефлексивную систему классов ради универсальности.

Архитектурные ограничения проверяются ESLint/анализом dependency graph и import-тестами на P01. Одного документа недостаточно. Проверки должны запрещать deep imports, cycles, framework/browser dependencies в домене и прямой случайный/временной API, но позволять соответствующие портовые адаптеры.

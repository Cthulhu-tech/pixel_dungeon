# Проверка переноса 1:1

Статус документа: требования к проверке. Эталонные fixtures, runnable oracle и тесты ещё должны быть созданы; этот документ не является отчётом об их прохождении.

## 1. Что должно совпасть

**Правила:** порядок и стоимость ходов, движение/автодвижение, ожидание, поиск, атаки и промахи, защита, урон, смерти, возрождение, голод, эффекты, AI, выпадение и идентификация предметов, экипировка, улучшения/деградация там, где они есть в исходниках, ловушки, растения, жидкости/области, магазины, NPC, задания, достижения и завершения забега.

**Контент:** все фактически присутствующие в baseline герои, существа, боссы, этажи и генераторы комнат, предметы, свойства предметов, эффекты, окна, тексты, звуки и изображения. Перечень устанавливается аудитом исходников, а не памятью об игре. Реестр должен учитывать специальные/редкие ветки; прохождение основного пути не доказывает полноту.

**Представление:** оригинальные asset frames, размеры тайлов, палитра/альфа, порядок слоёв, камера, туман, рамки окон, расположение кнопок, метрики текста, анимационные кадры и длительности, звуки и условия их воспроизведения. Не заменять оригинальный UI современными готовыми стилями rex.

**Состояние:** сохранение и продолжение всех значимых данных прохождения/профиля, корректная смена этажей, новая игра после завершения, очистка старых подписок и состояний. Не сохранять в качестве модели игры Phaser objects или XState runtime instances.

1:1 — поведенческое соответствие в определённых входных условиях, а не совпадение архитектуры и не произвольный pixel diff разных экранов/временных моментов.

## 2. Независимый эталон (oracle)

Зафиксировать: commit игры, commit PD-classes, способ сборки, Java/Android runtime, настройки, viewport, масштаб, locale, часы и условия ввода. Сначала доказать запуск совместимой исходной сборки либо работоспособность извлечённого Java-harness для конкретной подсистемы.

Fixture содержит provenance, начальное состояние, внешние входы, последовательность команд, RNG trace и прочие влияющие входы, ожидаемые checkpoints/events, при необходимости screenshot/audio timeline. Ожидаемые результаты создаются оригиналом. Ручной аналитический expected допустим для небольшого точно разобранного unit case с объяснением, но не заменяет независимый oracle для всей механики.

Не писать expected функцией из TS-порта, а затем объявлять совпадение доказанным. Обновление эталонного fixture требует причины и diff; запретить автоматическое «accept all screenshots» при приёмке.

## 3. RNG: сначала источник, затем seed

Прочитанный `PD-classes/com/watabou/utils/Random.java` использует Java `Math.random()`, float-преобразования, Int/IntRange и собственные shuffle/chances. У этого wrapper нет объявленного seed-контракта. Поэтому утверждение «одинаковый seed всегда даёт тот же Pixel Dungeon» до аудита неверно.

Для точного сравнения:

1. Ввести узкий RandomSource для выдачи исходных значений и совместимые функции исходного wrapper. В production домен не вызывает JS Math.random напрямую.
2. В независимом Java-harness записывать или контролируемо подавать последовательность исходных random draws, не меняя вычисления и места вызовов.
3. В TS воспроизводить ту же последовательность; сравнивать не только результат, но и число, порядок и потребителей draws.
4. Где исходная платформа/алгоритм PRNG подтверждены, отдельно проверить совместимый генератор и экспорт/восстановление его состояния. Сеянный replay сам по себе не доказывает соответствие оригиналу.

Особенно проверить exclusive/inclusive bounds, cast к float, нулевые и граничные веса, порядок суммирования вероятностей, пустые коллекции, shuffle и NormalIntRange. Граничные кейсы брать из исходного поведения, не «исправлять» привычным вариантом.

Инвентаризировать RNG-вызовы в эффектах/спрайтах. Если оригинальная графика потребляет общий поток, произвольное разделение на gameplay/cosmetic RNG меняет дальнейшие результаты. Сохранить потребление/порядок через совместимый адаптер или зафиксировать проверенное независимое разделение. Headless replay тоже должен учитывать эти draws. Не скрывать потенциально frame-dependent связь в оригинале: привязать fixture к recorded schedule и отдельно исследовать устойчивость.

## 4. Java ↔ JavaScript

В критичных формулах проверять:

- int division с усечением к нулю, а не Math.floor для отрицательных значений;
- Java cast, signed 32-bit arithmetic и shifts там, где они реально используются;
- float32-округление на тех стадиях, где исходник выполняет float-операцию/присваивание, а не один Math.fround в самом конце;
- различия float/double, порядок суммирования, special values и граничные сравнения;
- `Float.MIN_VALUE`/`Float.MAX_VALUE` в Actor, которые нельзя заменить JS Number.MIN_VALUE/MAX_VALUE;
- семантику строк/ID/enum и сериализации;
- порядок коллекций и равных приоритетов.

В Actor исходно используется HashSet, а при одинаковом времени берётся первый встреченный кандидат. JS Set с insertion order не является доказанной заменой. Записать порядок/выбор исходного runtime в fixtures, выяснить наблюдаемую стабильность и только потом выбирать representation. Если порядок оригинала не определён между запусками, фиксировать границы утверждения о паритете; не обещать универсальную bit-exact повторяемость и не вводить новый tie-breaker молча.

Порядок соседей Level, правила диагоналей/углов, блокировка существами, дверями и опасностями проверяются отдельно. Одинаковая длина пути не равна одинаковому пути. Не заменять поиск на A*, BFS, navmesh или библиотеку без проверки всей наблюдаемой семантики.

## 5. Время, команды и анимации

Логическое время хранится в turns. Проверять частичные стоимости действий, speed modifiers, создание/удаление actor, очередность buffs/blobs и ties. Результат не должен зависеть от того, сколько callbacks помещается в кадр браузера.

Однако исходный Actor.process() ждёт движущийся sprite и использует continuation через next(). Сопоставить mutation phases и callbacks каждого действия. Renderer подтверждает конкретный continuation ID; не вычисляет правила. Headless playback подтверждает их в эталонном порядке. Тестировать двойные/поздние подтверждения, прерывание сценой, restart и отсутствие зависших ходов.

`Dungeon.switchLevel()` использует локальный час для nightMode. Часы поступают через ClockPort; fixture задаёт конкретный час, включая границу 07:00. Не удалять эту зависимость под лозунгом детерминизма.

Сравнение при 30/60/144 FPS, throttling и background/resume выполняется с одинаковыми внешними входами; любые обнаруженные зависимости оригинала от визуального расписания документируются. У браузера не должно появиться новых ходов из-за real-time catch-up, если их не было в исходном сценарии.

## 6. Минимальная матрица проверок

| Область | Обязательные случаи |
| --- | --- |
| Random/числа | контрольные draws, boundaries, float32, веса, shuffle, порядок вызовов |
| Turns | несколько скоростей, ties, postpone, removal, buffs, death, callbacks |
| Grid | границы 32×32, диагонали, углы, двери, препятствия, занятые клетки, flee/seek |
| FOV/баллистика | стены/углы, двери, свет/темнота, невидимость по исходным правилам, траектория и остановка |
| Generation | каждый тип этажа/комнаты, несколько recorded traces, обязательные размещения, вход/выход, ловушки, heaps |
| Combat/AI | каждый отличающийся attack/defence/AI path, resistances, death side effects, boss phases |
| Items/effects | все зарегистрированные виды, identification, stacking, equip/use/drop/throw, сочетания и окончание эффектов |
| Run/profile | задания/NPC, магазины, разные окончания, badges/rankings, смена этажей, новая игра |
| Save | save/load round trip, все состояния из реестра, ссылки по ID, переход этажа, ошибка/повреждённые данные, поддержанные миграции |
| UI | каждое окно и состояние кнопок, targeting/cancel, inventory, журнал, настройки, сообщения, input locking |
| Lifecycle | новый забег после старого, возврат меню, повторные загрузки, restart сцен, cleanup |

Это начальная матрица, а не полный список fixtures. P00 расширяет её по найденному содержимому. Тест комбинаций не заменяется галочкой о наличии класса.

## 7. Графика и звук

Для изображений сохранять hash исходного файла, dimensions, alpha и frame definitions. Для преобразования атласа/шрифта сохранять скрипт и mapping; результат сверять, не править руками. Базовый режим использует оригинальное логическое разрешение/композицию и проверенный pixel scaling без растяжения пропорций; точные параметры извлекаются из исходников, не угадываются.

Снимать сравнения при зафиксированных logical viewport, DPR, camera, locale, RNG и presentation time. Статические пиксельные области должны совпадать точно; специфическую погрешность GPU/растрирования допускают только после локального объяснения и отдельного решения. Нельзя вводить широкий threshold, скрывающий неправильный шрифт или сдвиг UI.

Для анимаций сравнивать frame sequence, момент начала, длительность, callback-фазу и порядок. Для звука — asset, trigger, loop, громкость/высоту там, где их задаёт оригинал. Browser autoplay unlock — платформенный адаптер; он не повод заменять музыку или удалять сигналы. Не обещать sample-identical вывод разных аудиоустройств; сравнивать доступные контролируемые параметры.

## 8. Сохранения и платформенные отличия

Сначала описать исходные Bundle, class aliases, split game/depth files и все сохраняемые поля. Browser SaveRepositoryPort может использовать другое физическое хранилище и версионированные DTO, если сохранена наблюдаемая семантика. Не использовать имя минифицированного конструктора как persisted ID.

Совместимость импорта существующих Java-save проверяется отдельной задачей. Пока она не исследована/реализована, писать UNKNOWN/UNSUPPORTED, не «совместимо». До итоговой приёмки либо реализовать нужную совместимость, либо получить и записать явное решение о границе этой возможности. Не исключать её молча.

Android intents, back button, ориентация, vibration, filesystem, focus/resume и audio unlock перечисляются в матрице platform mapping. Очевидную замену ввода/хранилища оформлять как адаптер. Изменение доступной функции или поведения требует зафиксированного решения. Существенный неразрешённый разрыв не совместим с заявлением «полностью 1:1».

## 9. Критерий готовности

**VERIFIED для части:** найдены все относящиеся исходные ветки; реализовано поведение; соответствующие независимые parity fixtures прошли; нет открытого значимого расхождения; mapping/статус/тесты актуальны.

**Полный перенос:** полный source/content/UI реестр закрыт проверенными реализациями либо явно согласованными платформенными исключениями; все типы этажей, персонажей, предметов, боссов и окон проверены; доступны end-to-end прохождения и контроль редких веток; сохранения и cleanup проверены; сборка и архитектурные проверки проходят; release содержит необходимые исходники/уведомления; ограничения опубликованы.

До этого допустимы названия «частичный порт» и «реализовано, паритет не проверен». Ни зелёный build, ни красивый первый этаж, ни высокий line coverage сами по себе не означают 1:1.

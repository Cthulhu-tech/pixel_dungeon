# План полного переноса Pixel Dungeon 1:1

Обновлено: 2026-09-26 по согласованному в переписке порядку. Нумерация P00–P10 сохранена. Это план работ, не отчёт о завершённом порте. Обязательны [правила PSX/CORE в редакции порта](MANDATORY_RULES.md), [архитектура](ARCHITECTURE.md) и [критерии паритета](PARITY.md). Текущее состояние и evidence — в [STATUS.md](STATUS.md).

## 1. Конечный результат и границы

Полный браузерный перенос **игры из закреплённого исходного commit**, а не похожий roguelike и не Shattered Pixel Dungeon. Исходная версия — Pixel Dungeon 1.9.1 / versionCode 74; baseline указан в `source-baseline.json`.

| Требование | Что должно получиться |
| --- | --- |
| Игровое 1:1 | Все исходные правила, баланс, вероятности, AI, генерация, контент и последовательность действий |
| Визуальное/звуковое 1:1 | Исходные изображения, UI, текстовые метрики, анимации и звуки в заданных условиях сравнения |
| Переносимая архитектура | Изолированные владельцы логики, public APIs, явные зависимости, запуск domain tests без Phaser/браузера |
| Целевой стек | strict TS → JS, Vite, Phaser 4, XState, Zustand vanilla, phaser4-rex-plugins; navcat не установлен по умолчанию |

Внутреннюю Java-архитектуру копировать не требуется. Наблюдаемое поведение менять нельзя. Новые механики, ребаланс, другой арт, редизайн, новые классы/этажи и особенности PSX/CORE не входят в этот план. Сохранять авторство/лицензии; аудит ассетов — часть P00.

## 2. Что уже существует — не начинать с нуля

На проверенном checkpoint `6cc1858e1534b3b826e2ae0cf25e1bf52b2dd1d2` в main уже добавлены `tools/port/inventory.mjs`, его tests, generated inventory/summary, `source-map.json`, audit workflow и начальная заготовка `web/` с package.json, сценой, flows/stores и test files. Прежняя фраза «web и source-map не созданы» устарела.

Наличие файлов подтверждено чтением GitHub; полнота поведенческого покрытия, результаты тестов и совместная browser-работа этой документальной сессией не подтверждены. Существующий код сохраняется. Сначала сверить его с планом и новыми правилами, а не удалять и генерировать повторно.

В `web/package.json` есть `test:e2e` на Playwright: **агенту запускать запрещено** по PD-R20. Удаление/перестройка автоматической browser-проверки и остальные нарушения новых правил входят в P01-RULES; эта задача изменяет документацию, не runtime.

## 3. Порядок и контрольные точки

```text
P00: перечень + независимый эталон
P01: границы модулей + согласованная инфраструктура
             ↓
P02: точное ядро и алгоритмы
             ↓
P03: первый законченный игровой сценарий
             ↓
P04 генерация ↔ P05 акторы/бой ↔ P06 предметы/эффекты
             ↓
P07 полный цикл прохождения
             ↓
P08 полная UI/аудиовизуальная сверка + P09 полные saves/lifecycle
             ↓
P10 приёмка всего реестра
```

Стрелки P04/P05/P06 обозначают **координацию задач**, не разрешение циклических imports. Зависимости между модулями остаются ацикличными. P01 можно выполнять параллельно с запуском исходного oracle. UI и сохранения начинаются на P03 и расширяются вместе с механиками; их нельзя впервые интегрировать на P08/P09. Нет требования завершить весь контент одной ветки, прежде чем проверять связанные части другой.

**Пять контрольных результатов:** полный перечень → рабочая инфраструктура и точное ядро → первый законченный сценарий → весь исходный контент → подтверждённый полный перенос. Ни один промежуточный результат не называется готовой игрой 1:1.

## 4. P00 — полный перечень переноса и эталон

**Checkpoint:** IN_PROGRESS; file-level инструменты/реестр уже присутствуют, их проверки и полнота поведенческого перечня требуют сверки.

Первый результат — четыре связанных реестра:

| Реестр | Содержание |
| --- | --- |
| Логика | Ходы, grid, движение, бой, AI, генерация, предметы, эффекты, задания, saves |
| Контент | Все разновидности героев, существ, боссов, предметов, комнат, ловушек и других объектов |
| Интерфейс | Все экраны/окна, действия, состояния controls, targeting/cancel, переходы |
| Ресурсы/зависимости | Изображения, frames, шрифты, звук, текст, внешние классы, platform APIs |

Для каждой записи: source repository/commit/path/symbol, owner module, target files, зависимости, тесты/ручные сценарии, evidence и статус. File-level inventory не заменяет перечисление веток поведения и состояний UI.

### Подзадачи P00

- **P00.1. Инвентаризация исходников.** Проверить существующий инструмент против git tree baseline: tracked Java/ресурсы/ассеты, hashes, packages/classes/imports. Добавить пропуски, не пересоздавать уже сделанное и не считать индекс GitHub полным oracle.
- **P00.2. Реестр поведения и расхождений.** Проверить существующий source-map; дополнить четыре реестра и `discrepancies.md`. У каждой неперенесённой записи TODO, не VERIFIED. Учесть специальные/редкие пути, все HeroClass и отдельные окна.
- **P00.3. Внешняя PD-classes.** Проверить закреплённый candidate, требуемые imports, provenance и лицензии. Факт чтения/скачивания библиотеки не доказывает совместную сборку. Неподходящий pin меняется только по найденным доказательствам.
- **P00.4. Независимый oracle.** Подготовить воспроизводимый original Java/Android запуск либо подсистемный Java-harness. Инструментирование хранить отдельно от неизменного baseline и не менять правила. Агент не запускает браузер.
- **P00.5. Первые эталоны.** RNG draws/order, numeric cases, scheduler/continuations, путь, базовый бой; записать окружение, внешнее время и inputs. Screenshots/timing исходника и браузера получают разрешённым независимым способом; browser capture выполняет человек. Остальные fixtures добавляются вместе с задачами.
- **P00.6. Карта особых рисков.** Bundle/save/class aliases, глобальные состояния, random в presentation, HashSet ties, callback mutation phases, local time/nightMode, platform APIs, графика/текстовые метрики.

**Приёмка P00:** реестры покрывают закреплённые источники и значимые ветки; для первых переносимых систем есть независимые expected. Все неподтверждённые области имеют точный статус и не мешают независимым задачам. Не требуется заранее снять каждую возможную игровую ситуацию.

## 5. P01 — границы модулей, стек и обязательные ограничения

**Checkpoint:** IN_PROGRESS; начальная web-заготовка существует, gate и соответствие новым правилам не подтверждены.

До массового переноса записать владельцев:

| Модуль | Ответственность |
| --- | --- |
| compatibility | Java arithmetic/Random semantics, необходимые для исходного поведения |
| turns | Очередь, логическое время, стоимость действий, continuations |
| grid | Карта, occupancy/query, путь, FOV и траектории |
| generation | Этажи/комнаты и исходное размещение содержимого |
| actors | Герой/существа, характеристики, позиция, состояние AI |
| combat | Формулы и порядок разрешения атаки |
| items | Экземпляры, inventory/equipment, identification |
| effects | Временные состояния и их взаимодействия |
| quests | Правила и состояние заданий |
| run | Жизненный цикл прохождения, счётчики и переходы |
| profile | Постоянный прогресс, настройки, результаты |

Это модульный монолит. Публичный runtime API — `index.ts`; собственные type-only contracts — owner-scoped ambient `.d.ts` в `web/src/types/`. Не создавать пустые слои ради схемы. XState — orchestration; Zustand — UI projections; Phaser/rex — presentation.

### Подзадачи P01

- **P01-RULES. Согласовать существующую заготовку с MANDATORY_RULES.** Сохранить рабочие участки; убрать запрещённую browser automation из агентского gate, проверить/перенести типы в `.d.ts`, owner-local JSON/manifests, физические GLSL, explicit lifecycle, запрет fake fallbacks. Добавить статические policy tests. Не выдавать существующие проверки за уже покрывающие новые правила.
- **P01.1. Toolchain.** Проверить registry/engines/exports/типизацию фактически указанного набора пакетов; один package manager и lockfile, точные зависимости. Уже записанные версии — не доказательство совместимости. Не менять Phaser 4 на другую основу.
- **P01.2. Composition и контракты.** Public command/snapshot ports, один bootstrap, domain без framework/DOM, source state без дублирования.
- **P01.3. Минимальная интеграция.** Input → команда → domain operation → XState flow/UI projection → Phaser/rex presentation. Оригинальный sprite и control, один WebGL canvas. Non-UI project shader в `.glsl`, оригинальные pixels не меняются.
- **P01.4. Quality/tooling.** Действительные безбраузерные scripts для typecheck/build/unit/contracts/parity/boundaries/tools; missing parity evidence даёт NOT_READY, а не зелёный полный паритет. Никакого schema-validation path для доверенного контента. Руководство ручной browser-приёмки отдельно.
- **P01.5. Переносимость/документация.** Один чистый модуль собирается в минимальном Node host вместе только со своими `.d.ts`/чистыми dependencies. README owners, соответствующие RU/EN developer/recovery pages; единый PLAN не дублируется.

**Приёмка P01:** установка/typecheck/build и безбраузерные gates подтверждены реальными результатами; запрещённый import/type/shader/browser path обнаруживается; cleanup проверен контрактами. Реальные sprite/rex/input в браузере подтверждает человек. До его evidence полная integration/visual приёмка открыта.

## 6. P02 — точное ядро

Зависит от fixtures P00 и инфраструктуры P01 в используемой области.

Перенести Java numeric semantics (включая float32 и int casts), Random wrapper и контролируемый источник draws; проверять порядок потребления, а не обещать одинаковый seed для разных Math.random. Выяснить collection/tie semantics оригинала.

Перенести Actor scheduler: time/spend/postpone, add/remove, id, buffs/blobs, occupancy interactions, смерть, ожидание и `next()`/continuations. Сохранить исходные места mutations относительно animation callbacks.

Перенести исходные PathFinder, ShadowCaster, Ballistica: порядок соседей, диагонали/углы, препятствия, двери, занятость, flee/seek и остановки траектории. Navcat/A*/другой удобный алгоритм не заменяют оригинал без доказательства эквивалентности.

**Приёмка:** независимые Java/TS fixtures совпадают по состояниям, пути, событиям и RNG trace; ties и float boundaries покрыты. Headless adapter сохраняет continuation order; stale/двойные callbacks не добавляют ход. Нового влияния render FPS на игровые результаты нет; обнаруженные зависимости самого оригинала явно описаны.

## 7. P03 — первый законченный игровой сценарий

**Первый игровой результат:** запуск → начало игры → эталонный участок уровня → движение → встреча с противником → атака → подбор предмета → сохранение → загрузка → продолжение.

Использовать минимально необходимое **реальное поведение оригинала**: один герой, один противник, базовый предмет, соответствующие UI/анимации/звук. Это первый участок финальной архитектуры, не отдельная упрощённая игра. Неперенесённые действия не маскировать no-op/заглушкой.

Сразу добавить Save DTO/SaveRepositoryPort, round trip, независимый command/event trace, headless lifecycle test host, выход/новую игру и cleanup. Положение акторов и grid occupancy обновляются одной согласованной application-операцией, без наружного полусостояния.

**Приёмка:** public command-сценарий воспроизводится headless и совпадает с oracle; сохраняемое состояние восстановлено, фазы действий соблюдены, restart чистый. Человек проходит тот же сценарий в браузере и предоставляет evidence для UI/input/animation. Без него отмечается именно непроверенное представление, а не неподтверждённый полный DONE.

## 8. P04 — все этажи и генерация

Зависит от ядра/первого сценария. Координируется с P05/P06 по конкретным placements.

Перенести Level/Room/painters, все генераторы и подклассы этажей, terrain features, комнаты/соединения, двери/секреты, входы/выходы, квоты и размещения, traps/plants/heaps, особые/конечные этажи, повторное посещение и смену уровня.

Источник полного списка — `Dungeon.newLevel()` и исходный реестр: обычные зоны, пять боссовых этажей, LastShopLevel, LastLevel и DeadEndLevel. Не заменять их одним типовым генератором.

**Приёмка:** каждый generator учтён; для контрольных inputs/draws совпадают клетки, маски и содержимое. Проверены несколько независимых traces, обязательные placements и сохранённые этажи. Случайный smoke-run не заменяет сравнение. Конкретные mob/item интеграции закрываются совместно с P05/P06, а не отсутствующими заглушками.

## 9. P05 — герои, существа, AI и бой

Перенести все исходные HeroClass (Warrior/Mage/Rogue/Huntress), специализации/условия доступа, стартовые состояния, progression, Mob/NPC/boss разновидности, AI transitions, выбор целей/пути, атаки/защиту, resistances, эффекты смерти, опыт, respawn и боссовые фазы.

Задачи делить по различающемуся поведению, не только имени класса. Combat определяет расчёт/порядок, но не мутирует чужие коллекции напрямую; callbacks предметов/эффектов сохраняют исходные фазы. Не заменять всех AI на «идёт к герою и атакует».

**Приёмка:** каждому типу и особой ветке соответствуют implementation/fixtures; проверены зависимости скорости, оружия и эффектов. Нет generic fallback вместо неготового существа. UI/кадры и save codecs добавляются вместе с ним.

## 10. P06 — предметы, эффекты, интеракции

Перенести Generator, все inventory/equipment/consumable виды, bags/stacks, random labels/identification, equip/unequip/use/drop/throw, улучшения/деградацию и прочие реально присутствующие свойства. Перенести buffs/blobs/plants/traps: duration, stacking/refresh, interaction order, expiry/death и persistence.

**Один предмет переносится целиком:** получение → представление → доступные действия → применение → цена хода → взаимодействия → сохранение. Не создавать сначала сотню пустых классов. Сходство не повод объединять различающиеся правила оригинала. Данные — owner-local trusted JSON; поведение — явный TS, не универсальный DSL.

**Приёмка:** весь реестр видов/состояний покрыт; значимые сочетания, границы и save/load проверены. Уникальное поведение не заменено предметом с похожими цифрами.

## 11. P07 — полный цикл прохождения

Перенести NPC/quests/dialogues, торговлю/цены, journal/statistics, badges/rankings/challenges, главы и условия доступности, межэтажные переходы/падения/предметы, возрождения и все исходные завершения. Проверить reset/init глобальных состояний и независимость следующего забега.

**Приёмка:** от выбора героя до предусмотренных оригиналом окончаний работает полный public flow; profile/run разделены; сохраняется прогресс, нет чужого состояния между этажами/забегами. Редкие окончания проверяются целевыми fixtures, а не случайной ручной игрой.

## 12. P08 — закрыть весь UI, графику и звук

UI переносится с P03; этот этап — полное покрытие и сверка, не первое подключение интерфейса.

Перенести все Scene/Window/UI из реестра: меню/выбор/продолжение, HUD, inventory/item actions, inspect/targeting/cancel, диалоги, журнал, настройки, рекорды, результаты и доступность controls. Проверять открытие/закрытие/отмену/back, ввод/блокировки, touch и возврат в предыдущее состояние.

Сопоставить assets/frames/alpha, original metrics/font, chromes, layering, camera/fog, animation sequence/duration/callback, particles и audio triggers/loop/volume. Все conversions воспроизводимы; новых картинок нет. Project shaders только физические GLSL в одном Phaser WebGL runtime.

**Приёмка:** каждая экранная ветка и состояние есть в матрице; статические asset checks и доступные offline diff пройдены; человек предоставил browser evidence при заданных viewport/DPR/time/locale/inputs. Нельзя скрывать сдвиг UI/другой шрифт широким threshold. Нет browser evidence — соответствующая область NOT_VERIFIED.

## 13. P09 — полные saves и browser lifecycle

Контракты и round trip начаты на P03, codecs добавлялись с контентом. Завершить run/profile/floor persistence, stable references, полное восстановление состояний и согласованность game/floor writes. Разобрать исходные Bundle/aliases; явно назвать поддержанные импорты/внешние версии, не заявлять совместимость без проверки и не исключать её молча из итоговых границ.

Новая игра отдельно от load; повреждение/недостающие required fields/unsupported saves не исправляются скрытыми defaults, reset или fallback. Согласованное преобразование подтверждённого оригинального формата принадлежит boundary.

Проверить переходы/повторные сцены, pause/resume/focus, ночной режим через ClockPort, stale callbacks, аудио unlock и ненулевой production base path. Асинхронное хранилище не считается гарантированно сохранённым при unload. Проверки браузерного поведения выполняет человек, агент — headless contracts/build и анализ evidence.

**Приёмка:** save/load для каждого сохраняемого вида и ключевого состояния, переход/загрузка этажей, ошибки/прерывания, чистый restart; нет потерянных предметов/лишних ходов. Platform mapping и ограничения опубликованы, необследованные случаи явно открыты.

## 14. P10 — итоговая приёмка полного порта

| Вид проверки | Что доказывает |
| --- | --- |
| Полнота source/content/UI реестра | Ничего не забыто |
| Независимый behavioral parity | Перенесённое действует как оригинал |
| Архитектура/контракты/extraction | Владелец один, границы реальны, модуль выносится без приложения |
| Ручная browser/visual/audio проверка | Реальное представление/ввод/звук соответствуют, чего не доказывает build |
| Lifecycle/save/error проверки | Игра устойчиво работает целиком |

Пройти все классы, типы этажей, боссов, endings и специальные ветки. Сверить реестр без unmapped/ложных VERIFIED; запустить применимые безбраузерные тесты/typecheck/build/policy checks; проверить extraction с только нужными `.d.ts`. Человек проверяет браузер при заданных 30/60/144 FPS/нагрузке и повторных забегах; результаты привязаны к исходникам/настройкам, не заявляются по предположению.

Подготовить воспроизводимую сборку, release notes, лицензии, известные ограничения и поддержанные платформы. Публикация — отдельное поручение, не автоматическое следствие этой задачи.

**Полный DONE:** все записи VERIFIED либо имеют явное согласованное платформенное исключение; значимых открытых расхождений нет; ручное evidence там, где оно нужно, получено. Красивый первый этаж, успешный build или высокий line coverage этого не заменяют.

## 15. Формат конкретной задачи и статусы

Одна задача — законченное наблюдаемое поведение: применение зелья, переход этажа, обнаружение героя определённым mob. Для тесно связанного поведения допустима небольшая группа, а не десятки косметических правок.

```text
ID / цель / этап:
Source: repository@commit:path#symbol
Owner module и единственный источник состояния:
Зависимости / public contracts / declarations:
Полный список переносимых веток:
Затронутые UI, animations, saves, assets/locales:
Независимые fixtures / происхождение expected:
Ручной browser-сценарий, если нужен:
Критерии готовности:
Результаты реально выполненных команд и evidence:
Расхождения / блокеры / непроверенное:
Статус / следующий шаг:
```

Статусы: TODO, IN_PROGRESS, IMPLEMENTED_UNVERIFIED, VERIFIED, BLOCKED. Допустимое платформенное исключение хранится отдельной записью с решением, а не удалением работы из реестра. **«Реализовано» не равно «проверено против оригинала».** Запрет browser automation не отменяет финальную visual приёмку.

## 16. Следующий шаг после записи плана

Не запускать реализацию автоматически из этой документальной задачи. При следующем поручении продолжать: сверить существующие результаты P00.1/P00.2, довести полный поведенческий/UI перечень; затем P01-RULES и независимая подготовка oracle P00.3–P00.6. Сохранить готовые участки и evidence, не обнулять их. После этого двигаться к точному ядру и первому сценарию P03.

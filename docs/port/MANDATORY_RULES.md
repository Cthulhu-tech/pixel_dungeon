# Обязательные правила Pixel Dungeon

Дата: 2026-09-26. Этот файл — действующие ограничения исполнения, а не рекомендации. Нарушение применимого правила блокирует VERIFIED/DONE. Цель остаётся прежней: полный перенос закреплённого Pixel Dungeon 1:1, SOLID / KISS / DRY / OOP / DDD, выбранный браузерный стек.

## Происхождение и область переноса

Правила перенесены по поручению пользовательницы из двух её репозиториев, а не придуманы по названиям проектов:

- **PSX:** `Cthulhu-tech/psx@9adcf519b8e47c3bdbc5e5c52b78f418715e597f`, `AGENTS.md`, `docs/agent/MANDATORY_RULES.md`, `docs/agent/protocols/PRE_TASK.md`.
- **CORE:** `Cthulhu-tech/core-@8b8d7aed0808d2f809de542e77c47f7e53b91915`, `AGENTS.md`, `ARCHITECTURE.md` (общие правила), `.codex/context/index.md`, `.codex/context/core.md`, `.codex/context/quality.md`; также прочитаны относящиеся к presentation/content разделы контекста.

Ниже зафиксирована применимая к Pixel Dungeon редакция. Сведения о частных игровых заданиях, ресурсах, балансе и реализации PSX/CORE не становятся требованиями этой игры. Эти репозитории не являются runtime/build-зависимостями порта; для работы достаточно здешнего контекста. Не копировать приватные конфигурации, токены, окружение или купленные ресурсы вместе с правилами.

При расхождении: новое явное поручение пользовательницы → цель и выбранный стек Pixel Dungeon → этот файл и его таблица адаптаций → предметные документы и текущая задача. Исторический документ не отменяет актуальное правило. Новые неразрешённые конфликты записывать, а не выбирать удобную трактовку молча.

## A. Работа с контекстом и задачами

### PD-R01. Сначала контекст и владелец

Перед изменением читать `AGENTS.md`, этот файл, актуальный `STATUS.md`, активную задачу `PLAN.md`; затем только затронутые модули, публичные контракты, вызывающий код и исходные методы baseline. До реализации назвать владельца данных, зависимости, lifecycle, затронутый контент и проверки. Для нового UI сначала искать существующий control. Не перечитывать всю историю после каждой правки; после потери контекста восстановить действительный checkpoint. Источники: PSX PRE_TASK, ARC-001/008/010; CORE context router/quality.

### PD-R02. Одна очередь, без сброса прогресса

`PLAN.md` — единственная очередь P00–P10; `STATUS.md` — факты текущего checkpoint; source-map — соответствия и evidence. Issues/чаты/старые отчёты не создают вторую очередь. Не перенумеровывать задачи, не обнулять статусы, не переписывать существующий код с нуля и не затирать чужие изменения. Переход от правил к коду не разрешён задачей, которая просит только документацию. Источники: PSX AGENTS; CORE index.

### PD-R03. Короткие законченные изменения и честный отчёт

Выбирать простейший корректный путь, не проводить повторный общий аудит без конкретного вопроса. Исправлять причину дефекта у владельца, добавлять regression test; не маскировать баг задержкой, дублирующим флагом, fallback или catch без обработки. Целевые тесты — после законченного изменения; полный применимый набор — на checkpoint. Не повторять неизменный прогон без причины. Отчёт содержит реальные команды/результаты, source revision, непроверенное и следующий шаг. Источники: PSX режим «без микротюнинга», ARC-006/007; CORE quality.

## B. Архитектура и типы

### PD-R04. Один владелец каждого изменяемого факта

HP, предмет, эффект, очередь ходов, профиль и настройки имеют по одному authoritative owner. Кэш/проекция явно называют источник и пересоздаются из него; не изменяются как второй источник истины. XState владеет orchestration, Zustand vanilla — UI-проекциями/локальным UI-состоянием, Phaser/rex — представлением. Сохранённый snapshot не становится вторым live store. Источники: PSX ARC-002/029; CORE core/ARCHITECTURE; распределение библиотек уточнено для Pixel Dungeon.

### PD-R05. Изолированные переносимые модули

Модуль имеет одну самостоятельную ответственность, `index.ts`, README, необходимые owner-local данные и изолированные тесты. Runtime-вызовы соседей идут через public API, команды, DTO, события и узкие порты. Deep imports, циклы, прямой доступ к чужому store, god object и общая свалка utils/helpers/managers запрещены. Домен не импортирует Phaser/rex/XState/Zustand, DOM, storage, audio или адаптер. Класс для сущности с инвариантами, функция для алгоритма, данные для таблицы: не создавать классы/слои без смысла. Источники: PSX ARC-001/004; CORE core/architecture.

### PD-R06. Один composition root; импорт без побочных эффектов

Создание и связывание основных экземпляров выполняется явно в bootstrap. Импорт не запускает renderer, сцену, actor XState, подписку, worker, таймер, чтение save или loop. Service locator, поиск зависимости по строковому имени и изменяемые глобальные singleton registries запрещены. Чистые декларации типов не являются разрешением на глобальное runtime-состояние. Источники: PSX ARC-003/050–052; CORE architecture.

### PD-R07. Типы только в owner-scoped ambient declarations

Все **собственные** `type`, `interface` и type-only контракты проекта объявляются только в `web/src/types/**/*.d.ts`. В `.ts/.js/.mjs` такие объявления запрещены. Не импортировать, не экспортировать и не re-export типы; исходники используют глобальные имена напрямую. Runtime классы, функции и значения по-прежнему экспортируются через `index.ts`. Не переписывать поставляемые библиотеками декларации.

Чтобы сохранить требование выноса модулей: декларации разделить по владельцам (`types/turns/`, `types/grid/`, `types/contracts/`), использовать однозначные имена вроде `PDTurnCommand`, перечислять зависимости в README. При извлечении копировать только модуль, его declarations и объявленные чистые зависимости. Изолированный typecheck не должен подключать весь общий `src/types` и тем самым скрывать связи. Ambient globals — compile-time convention, не глобальное владение данными. Источник: CORE core; owner-scoping и extraction gate — адаптация к DDD этого порта.

### PD-R08. Строгая типизация без обходов

Запрещены `any`, `@ts-ignore`, фиктивные typings ради зелёной сборки, необоснованные assertions/non-null assertions и цепочки casts, скрывающие ошибку контракта. Внешние неизвестные данные входят как unknown и разбираются у своей недоверенной границы. Не отключать strict/checks глобально. Исправлять контракт, а не обходить его. Источники: PSX ARC-004; CORE core.

### PD-R09. Структурированное поведение

Команды и runtime state — типизированные структуры со стабильными ID. Запрещено реализовывать игровые правила переписыванием строк, generated/eval JavaScript или строковыми патчами состояний. Форматирование исходного текста/локализации не равно изменению модели. Не строить свой универсальный DSL или новую событийную платформу без реальной задачи. Источники: CORE core; PSX declarative/semantic boundaries.

## C. JSON, контент, ресурсы

### PD-R10. JSON принадлежит владельцу

Извлечённые таблицы оригинала, настраиваемые значения и asset declarations принадлежат модулю/адаптеру и хранятся в его `assets/`; никакой общей свалки игрового контента. Gameplay ссылается на стабильный content/Asset ID, не физический URL, Phaser handle или имя конструктора. Render frame/path разрешается в presentation. Сохранить ровно исходные значения и порядок таблиц; это извлечение, не новый баланс.

**Исключения по смыслу:** исходные `assets/`, `src/`, `res/` неприкосновенны и не переносятся ради структуры; общий source-map/inventory — аудит, не runtime content owner. Build может копировать исходные bytes без изменения по owner-local manifests. Общая композиция загруженных ссылок не создаёт второй каталог-владелец. Источники: PSX ARC-005/082/083; CORE immutable content.

### PD-R11. Собственный JSON доверенный и неизменяемый

Для авторского/извлечённого **проектного контента** запрещены runtime и build-time schema-validation, sanitization, normalization, coercion, injected defaults, defensive cloning/freezing и отдельный content-validation pipeline. Использовать compile-time типы и загруженные данные напрямую, не записывать в них runtime state. Обычное декодирование JSON при загрузке необходимо; запрет относится к дополнительному преобразующему/валидирующему слою.

Это не запрет на проверки недоверенного ввода, save/import/network, команды игрока и инвариантов домена. Ошибки загрузки видны. Source inventory, сверка hash/provenance, тесты исходных формул и семантическое сравнение с оригиналом — обязательная проверка паритета, не нормализатор авторского JSON. Источники: CORE core/ARCHITECTURE/quality; PSX ARC-007.

### PD-R12. Читаемый JSON без версий внутреннего формата

Новый/изменяемый репозиторный JSON — полный pretty-format: два пробела, развёрнутые вложенные массивы/объекты, завершающий newline. Не добавлять `schemaVersion`, `formatVersion` и подобные поля, служащие только версии внутреннего shape. При содержательном изменении старого файла согласованно обновить его writer/readers и убрать такое поле; не ломать существующий генератор отдельной косметической правкой.

Идентичность исходной игры (`manifestVersionName`, versionCode), версии npm-пакетов/lockfile, содержательные значения оригинала и versions внешнего save/wire envelope — не версии внутреннего JSON shape; их не удалять. Baseline источников остаётся закреплённым. Источник: PSX ARC-005 и PRE_TASK.

### PD-R13. Загрузка, ошибки и реальные ресурсы

Один фактический запрос на общий Asset ID, общий владелец ресурса и понятный срок жизни. Загрузка публикует готовность только завершённой стадии; stale async result отвергается по generation/run/level ID. Progress берётся из реальных задач/bytes, не из таймера или случайных процентов. Broken source/manifest, missing required resource и failed load — явная ошибка, не заглушка, молчаливый reset или вечная загрузка. Не вводить отдельные managers/worker pools для каждого потребителя. Источники: PSX ARC-072/076–094; CORE core.

### PD-R14. Оригинальный текст и reusable UI

Пользовательские строки извлекать в локализацию со стабильными ключами, сохраняя исходные текст, placeholders, порядок и условия показа. Поддерживаемые языки определяются baseline/отдельной задачей, не числом языков PSX. Изменение текста обновляет соответствующие locale data; не добавлять новый язык или перефразирование в рамках 1:1. Повторяющийся control делается один раз через public UI API; reuse/variant/composition прежде копии. Нельзя менять оригинальное оформление ради удобства готового виджета. Источники: PSX ARC-009/010/045; CORE quality/content.

## D. Presentation, время, lifecycle

### PD-R15. Один Phaser WebGL runtime

Один Phaser 4 game canvas и один основной presentation loop. Phaser/rex владеют только картинкой/вводом; Canvas-renderer fallback, второй renderer/context, игровой DOM/HTML overlay и отдельные игровые loops запрещены. HTML-контейнер запуска не является игровым UI. Нет React/Three/WebGPU-движка, добавленного вслед за PSX. Источники: CORE core/presentation; принцип одного runtime из PSX ARC-053 адаптирован к выбранному стеку.

### PD-R16. Shader-only world; исходники shader только в файлах

Вся не-UI графика проходит через проектный shader path Phaser WebGL. UI — единственное исключение из требования выделенного проектного shader, но тоже рисуется Phaser/rex в том же WebGL canvas. Каждый **проектный** shader stage хранится в отдельном осмысленно названном `.glsl` внутри owning presentation adapter, например `adapters/phaser/shaders/world-sprite.frag.glsl`.

Запрещены shader source, генерация/склейка/патчинг shader-кода в `.ts/.js/.mjs`, template literals и строках. Host импортирует физический source и передаёт параметры. Это не требование переписать внутренности Phaser или vendor dependencies. Для порта используются исходные sprite textures; shader не перерисовывает арт и не меняет пиксели/эффекты оригинала. Нет требования отдельного shader на каждый предмет: использовать общие подходящие pipelines. Источники: CORE core/presentation; PSX ARC-204 (.wgsl заменён на .glsl по стеку).

### PD-R17. Только исходная экономика ходов

Игровые команды проходят application coordinator и владельца исходной очереди. `delta`, визуальное положение спрайта, camera shake и качество графики не становятся источником HP, положения, AI или стоимости хода. Не переносить из PSX fixed-step физику или из CORE интервалы добычи: scheduler Pixel Dungeon переносится с собственной семантикой.

При этом исходные `sprite.isMoving`, callback-фазы и `Actor.next()` нельзя выбросить. Presentation подтверждает конкретный continuation, домен/application решает, что продолжить. Headless adapter сохраняет порядок; stale/повторный acknowledgement не создаёт дополнительный ход. Источники: PSX ARC-020–024/035; CORE ownership; исключение обусловлено исходным Actor.

### PD-R18. Явный lifecycle и очистка

Инициализация идёт dependencies → consumers; teardown — обратно. Разделять application и run/scene scopes. Каждый listener, actor subscription, resource, timer, pending job и worker имеет владельца и очистку. Stop/dispose идемпотентны. Частичный startup failure откатывает реально достигнутые стадии и не публикует RUNNING. Старый run не может дописать состояние в новый. Импорт ничего не запускает. Источники: PSX ARC-LIFE-001–004/058/091/094; CORE quality.

### PD-R19. Оптимизация без фанатизма и изменения игры

Сначала подходящий алгоритм, ограниченные очереди/память, reuse ресурсов, отсутствие ненужных копий и повторной работы. Неподвижный/выключенный эффект не обновляется бессмысленно; invalidation и восстановление сохраняются. Batching/pooling/worker использовать при реальной выгоде, не создавать infrastructure ради 32×32 карты.

Дальнейшая оптимизация — по воспроизводимому bottleneck и сопоставимым измерениям. Не микротюнить косметические выражения и не повышать budget ради зелёного отчёта. Не урезать AI, контент, точность, cleanup или визуальное качество оригинала. Внешняя ручная browser evidence и безбраузерные benchmarks имеют разные области доказательства. Источник: PSX AGENTS, режим от 12 сентября; CORE quality.

## E. Проверки, сохранения, репозиторий

### PD-R20. Агенту запрещён запуск браузера

**Агент/Codex не запускает, не подключает и не автоматизирует браузер:** Chrome/Edge/Chromium, CDP, Playwright, Puppeteer, browser-based runtime checks и любые запускающие их scripts. Не обходить запрет через удалённый браузер, дочерний процесс, workflow или npm wrapper. Проверять содержание команды перед её запуском.

Разрешены чтение исходников, Java/headless oracle, Node tests, typecheck, build без auto-open, проверка imports, статический анализ GLSL и offline comparison уже полученных эталонов. Реальное отображение/звук/ввод в браузере проверяет человек; агент готовит сценарий и анализирует полученные артефакты. При отсутствии evidence статус визуального/runtime паритета **NOT_VERIFIED**, а не «прошёл по сборке». Браузерная приёмка остаётся обязательной для полного 1:1. Источники: CORE AGENTS Browser prohibition, quality 6–7.

### PD-R21. Настоящие тесты и полный паритет

Изменение runtime/контракта/рендера/политики покрывается применимыми безбраузерными tests; TS — typecheck; runtime/assets/config — build; границы — architecture gate. Изменение документации требует проверки ссылок, согласованности и diff, но не выдуманного запуска runtime. Не добавлять content schema validation вопреки PD-R11.

Ожидаемые игровые результаты получают из независимого оригинала, не самим тестируемым портом. Сквозной headless тест идёт через публичную команду/coordinator, не подменяет путь прямой мутацией presenter. Пустые/skipped suites не подтверждают паритет. Визуальные факты требуют ручного evidence. Не ослаблять thresholds, не обновлять expected автоматически ради зелёного результата. Источники: PSX ARC-007/060/194; CORE quality; PARITY.md.

### PD-R22. Save без молчаливого восстановления

Новая игра и загрузка существующей — разные операции. У save один владелец, stable IDs, согласованные snapshots; нет Phaser handles/минифицированных constructor names. Не подставлять недостающие поля, не сбрасывать прогресс и не загружать неподдержанный формат «примерно».

Импорт оригинального Bundle/save и версии внешнего save envelope исследуются в P00/P09: явно перечислить поддерживаемое, реализовать только доказанное преобразование у persistence boundary. Java arithmetic/serialization compatibility для 1:1 разрешена и необходима; запрет CORE на собственные старые saves не переносится как запрет совместимости с эталоном. Никаких незаявленных fallback readers и dual legacy pipelines. Источники: CORE core/quality; PSX ARC-068; адаптация под порт.

### PD-R23. Документация меняется вместе с контрактом

Изменение ownership, lifecycle, public API, данных или setup обновляет README владельца, соответствующий port context, mapping/task evidence и STATUS в той же задаче. Поддерживаемые русская/английская страницы не должны противоречить друг другу; перевод не создаёт вторую очередь задач. Сейчас операционный контекст порта русский; RU/EN developer/recovery pages заводятся с соответствующими модулями на P01 и поддерживаются вместе. Источники: PSX ARC-008; CORE quality; языковой layout адаптирован без дублирования backlog.

### PD-R24. Чистое дерево и неизменяемый оригинал

Новый runtime только в `web/`; исходные Java/ресурсы/manifest/license не переписывать. Scratch, временные логи, previews и raw traces — только root `tmp/`, игнорируемый Git; не плодить `.tmp-*`. Канонические reference fixtures с provenance и компактные отчёты — намеренные versioned артефакты, не scratch. Не коммитить `dist`, browser profiles, node_modules, copied worktrees или секреты. Одна выбранная package-manager конфигурация/lockfile, не параллельные установки. Источники: CORE core; PSX ARC-190; ограничения baseline порта.

## Явные адаптации: что НЕ переносится механически

| Исходное требование | Действующая редакция Pixel Dungeon |

| PSX fixed-step physics; CORE mining cadence | Исходная пошаговая очередь Pixel Dungeon с точными callback-фазами |
| PSX Navcat обязателен | Здесь только кандидат; исходный клеточный алгоритм первым |
| PSX двадцать save slots; CORE три слота и progression/ore/pet правила | Только исходное поведение Pixel Dungeon; числа и контент других игр не переносятся |
| CORE types в корневом src/types | `web/src/types/<owner>/*.d.ts` плюс обязательный isolated extraction/typecheck |
| CORE JSON trust против PSX owner schema parsing | Доверенный контент без валидаторов; неизвестные external saves/commands проверяются у границы |
| CORE no compatibility против переноса Java | Запрет скрытых workaround/fallback, но явная numeric/original-save compatibility необходима для 1:1 |
| PSX browser performance gate против CORE Browser prohibition | Безбраузерный automated gate; browser evidence только ручной; недостающие доказательства не становятся DONE |
| PSX owner-local assets против исходного assets/ | Исходные bytes и пути эталона неизменны; новые definitions/manifests owner-local |

Это не разрешение упрощать игру. Если правило нельзя выполнить без нового изменения поведения, фиксировать конкретный конфликт до соответствующей реализации. Разрешённые независимые задачи продолжаются.

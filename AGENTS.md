# Pixel Dungeon: обязательный контекст переноса

## Цель и границы

Перенести **игру из этого репозитория полностью 1:1** с Java/Android на браузерный JavaScript. Основной исходный код нового приложения — TypeScript; сборка — Vite; отображение — Phaser 4; управление сценариями приложения — XState; UI-проекции — Zustand vanilla; компоненты UI — phaser4-rex-plugins. **navcat только кандидат, не обязательная зависимость.**

Эталон: `Cthulhu-tech/pixel_dungeon@ce7f241515fd5c040fcf18b4beb5b7a49d9d535f`, манифест Pixel Dungeon **1.9.1**, versionCode **74**. Это оригинальный Pixel Dungeon, не Shattered Pixel Dungeon и не сторонний TS/PixiJS-порт. Не подменять эталон другой игрой, новой upstream-версией или описанием из интернета.

1:1 означает совпадение правил, контента, поведения, интерфейса, графики, анимаций и звуков в согласованных условиях сравнения. Это НЕ требование сохранить Java-пакеты, Android API, статические глобальные объекты или структуру классов. Архитектуру менять можно; наблюдаемую игру — нельзя. Прототип, вертикальный срез и «похожий roguelike» не являются завершённым переносом.

Прочитать в таком порядке:

Файлы репозитория — переносимый контекст проекта. Решения не должны существовать только в чате или в памяти агента. Новое явное решение пользовательницы обновляет соответствующий документ; нельзя самовольно менять требования, чтобы закрыть задачу.

## Неприкосновенный эталон

- Не удалять, не переносить и не переписывать исходные `src/`, `assets/`, `res/`, `AndroidManifest.xml`, `LICENSE.txt`. Новый браузерный проект размещать в `web/`.
- Эталон читать по зафиксированному commit, а не по подвижному HEAD. Смена baseline — отдельное явно согласованное решение.
- `PD-classes` — необходимая внешняя часть оригинала. Её кандидат commit и непройденная проверка совместимости записаны в baseline. Не объявлять внешний код проверенным только потому, что найден репозиторий.
- Для каждого переносимого поведения сохранять происхождение: repository + commit + path + symbol, целевые файлы и тесты. Один Java-файл может соответствовать нескольким TS-модулям, и наоборот.
- Сохранять авторство и лицензионные уведомления. Не выдавать порт за оригинальную разработку. Инвентаризация ассетов включает их происхождение и условия использования.

## Архитектурные правила: SOLID / KISS / DRY / OOP / DDD

- Строить **модульный монолит**, не микросервисы и не самодельный универсальный движок.
- Разделять предметные области и назначать ровно одного владельца каждому изменяемому состоянию. Внутри игрового контекста выделять небольшие модули правил: очередь ходов, сетка, генерация, акторы/AI, бой, предметы, эффекты, задания.
- Каждый модуль имеет явный публичный API, собственные тесты и только необходимые зависимости. Папки `domain/`, `application/`, `ports/` добавлять по необходимости, без пустых слоёв ради шаблона.
- Чужие внутренности не импортировать. Циклические зависимости запрещены. Модули связывать через узкие типизированные контракты и composition root.
- Домен не импортирует Phaser, rex, XState, Zustand, DOM, WebAudio, browser storage или инфраструктурные реализации. Он должен проверяться в Node без canvas и браузера.
- OOP использовать для сущностей и объектов с инвариантами; функции — для алгоритмов; данные — для таблиц и DTO. Не создавать класс ради класса. Предпочитать композицию; наследование допустимо для реального отношения подстановки, а не для общего доступа к состоянию.
- SOLID: одна причина изменения; небольшой интерфейс под клиента; зависимости через конструктор/фабрику; подстановки подтверждаются контрактными тестами; расширения контента не должны требовать правок несвязанных областей.
- DRY относится к одному правилу и одному источнику данных. Не объединять похожие, но различающиеся правила оригинала. Не создавать универсальную систему эффектов/скриптов без реальной потребности.
- KISS: сначала самый простой вариант, сохраняющий поведение. Запрещены бессодержательные BaseManager/BaseService, глобальный service locator, общий mutable GameState для всех модулей и EventBus как замена явным зависимостям.
- Нет жёстких лимитов строк или требования «интерфейс на каждый класс». Обоснование абстракции — реальная граница, тестирование или возможность вынести модуль.

## Единственный источник состояния

- Доменные объекты владеют HP, инвентарём, картой, эффектами, AI и экономикой ходов.
- XState владеет сценарием приложения и взаимодействия: загрузка, меню, запуск/продолжение, выбор цели, ожидание команды/визуального подтверждения, выход. Не заменяет исходный планировщик ходов.
- Zustand через `zustand/vanilla` хранит read-only для потребителей UI-проекции и локальное UI-состояние. Не является вторым владельцем HP, инвентаря или карты.
- Phaser/rex отображают состояние и преобразуют ввод в команды. Обработчик кнопки не рассчитывает урон и не списывает предмет.
- Один факт может быть отображён в нескольких проекциях, но изменён только у владельца. Проекция пересоздаётся из домена, обратная мутация запрещена.

## Приоритет точности

- Не менять баланс, вероятности, количество/условия действий, AI, путь, FOV, порядок эффектов, цены, генерацию, контент, тексты или интерфейс «для улучшения».
- Не исправлять наблюдаемое поведение оригинала попутно. Подозрительный баг заносить в журнал расхождений. Безопасность и реальные ограничения браузера разбирать явно, а не маскировать под паритет.
- Не заменять алгоритм более привычным, пока не доказано совпадение его наблюдаемых результатов. Это особенно важно для PathFinder, ShadowCaster, Ballistica, очереди ходов и Random.
- Не использовать `Math.random()`, `Date.now()`, Phaser RNG и таймеры напрямую в домене. Случайность и внешнее время приходят через порты; точные правила сравнения заданы в PARITY.md.
- Сохранять Java-семантику вычислений там, где она влияет на результат: float32, целочисленное деление, casts, переполнение, порядок коллекций. Не заменять всё механически JS number/Set.
- Игровое время не равно `delta` кадра. При этом исходные паузы/продолжения через завершение анимации тоже являются поведением и должны быть сохранены через явный протокол, а не отброшены.
- Не генерировать и не перерисовывать ассеты. Использовать оригиналы с проверкой рамок, альфы, палитры, метрик шрифта и таймингов. Любые конвертации должны быть воспроизводимыми.

## Как переносить одну часть

1. Найти все исходные входы, зависимости и побочные эффекты выбранного поведения.
2. Зафиксировать случаи сравнения и ожидаемый результат, полученный из оригинала. Не генерировать expected тестируемым TS-кодом.
3. Перенести минимальную законченную часть в нужный модуль.
4. Добавить unit/contract/parity-тесты; для UI — эталонные изображения и сценарий ввода.
5. Проверить интеграцию, сохранение/загрузку и cleanup там, где они затронуты.
6. Обновить mapping, статус задачи и известные расхождения; затем коммитить.

Не объявлять DONE по факту наличия файлов или успешной сборки. Статус без эталонных проверок — IMPLEMENTED_UNVERIFIED, не VERIFIED. Нельзя незаметно пропускать классы, классы героев, предметы, окна, боссов или специальные случаи. Нет «потом доделаем», скрытого за успешным статусом.

## Поведение при блокировке

Если не хватает внешнего источника, исходной сборки, fixture или решения о платформенном отличии, зафиксировать точный блокер и его область. Продолжать независимые задачи. Не выдумывать правила; не останавливать весь проект, если заблокирована только одна часть. Запрещено переименовывать блокер в «поддержано» или подменять оригинальную механику заглушкой.

## Проверки и отчёт

Команды установки, typecheck, lint, unit/parity/e2e, build и проверки границ должны реально появиться в `web/package.json` и CI на этапе P01. До этого не утверждать, что они существуют или запускались. Один выбранный package manager и один lockfile; версии фиксируются после проверки фактической совместимости.

В конце каждой рабочей сессии обновлять STATUS.md: что действительно изменено, какие проверки реально запущены и с каким результатом, оставшиеся блокеры, следующий конкретный шаг. Отделять написанный код, проверенное поведение и документированный план. Никаких придуманных процентов готовности и результатов тестов.
